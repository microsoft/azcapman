## Why

This is the single highest-value open question in this research sprint — it was never directly tested in prior sessions (only Claude Code and Copilot CLI symlink behavior were verified).

## Research subagent result (received)
Status: **research phase complete, symlink question substantially resolved (with one remaining edge case), plus corrections.**

- **Symlink verdict**: Codex's own docs (learn.chatgpt.com/docs/build-skills.md) state Codex "supports symlinked skill folders and follows the symlink target when scanning these locations" — a top-level skill-dir symlink IS documented-safe. BUT this does not cover symlinks *inside* a skill pointing outside the skill root (azcapman's actual ~62-pointer case). Docs document a `--sparse` flag and a `"source": "git-subdir"` marketplace source type for remote/git installs — a sparse checkout of just the skill subdirectory would leave those 62 external symlinks dangling. **No source confirms the default fetch mechanism (full clone vs sparse) for git-subdir installs.** Verdict: UNRESOLVED for the azcapman case; real, docs-confirmed risk.
- **Required fallback (per acceptance criterion 2)**: do not rely on symlinks for skill-internal content; copy `docs/`, `vendor/`, `scripts/` targets into the skill's own `references/`/`scripts/`/`assets/` subdirs instead.
- **Correction**: marketplace path — current canonical is `$REPO_ROOT/.agents/plugins/marketplace.json`; `.claude-plugin/marketplace.json` is read only as a **legacy-compatible fallback**, not the primary path.
- **Correction**: user-scope skills live at `$HOME/.agents/skills`, NOT `~/.codex/` (that's the Codex config home, for config.toml/AGENTS.md only).
- Confirmed: `"skills"` is a single string path in plugin.json (not array); AGENTS.md discovery/32 KiB cap/root-to-CWD-walk all confirmed; no plugin.json/marketplace.json validator exists.
- Unverified (flagged, not asserted): exact TOML-subagent path (`~/.codex/agents/`), hook lifecycle event count (~11 claimed, only `SessionStart` confirmed).

**Action needed before rebuild**: restructure the skill to use real file copies instead of symlinks for anything the skill itself must read, given the unresolved git-subdir/sparse risk.

## RESOLVED via direct source-code verification (follow-up pass)
Status: **DEFINITIVE. Question fully resolved — symlink handling confirmed BREAKING for azcapman's use case.**

Source: `codex-rs/file-system/src/lib.rs`, function `walk_via_directory_reads`:
```rust
if metadata.is_symlink && (!options.follow_directory_symlinks || !metadata.is_directory)
{
    continue;
}
```
Permalink: https://github.com/openai/codex/blob/57f42a81131ccf5933e7ec5dc659c381eeb5d72b/codex-rs/file-system/src/lib.rs#L337-L340

- **Directory symlinks** (the skill folder itself being a symlink) ARE followed — confirmed by `DirectorySymlinkPolicy::Follow` set for User/Repo/Admin scopes in `codex-rs/core-skills/src/loader.rs`. This matches the docs statement about "symlinked skill folders."
- **File symlinks** (a symlink *inside* a skill directory pointing to a file elsewhere — azcapman's exact ~62-pointer structure) are **unconditionally skipped** by the walker, regardless of any policy setting. `codex-rs/core-skills/src/loader/discovery.rs` only processes `WalkEntryKind::File` entries as skill candidates; skipped symlinks never reach that stage.

**Conclusion: Codex will never discover or read azcapman's file-symlink-based skill content.** This is not a git-subdir/sparse-checkout edge case — it fails even on a full local clone, because the walker itself drops file symlinks before any git-fetch mechanism is even relevant.

**Action required (upgraded from "recommended fallback" to "mandatory"): the skill must use real file copies, not symlinks, for any `docs/`, `vendor/`, `scripts/` content Codex needs to read.** This requirement is now unconditional and confirmed by source, not inferred.
