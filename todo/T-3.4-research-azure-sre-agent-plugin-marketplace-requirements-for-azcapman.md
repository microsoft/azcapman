## Goal
Produce a cited, AGENTS.md-compliant requirements doc for rebuilding the Azure SRE Agent plugin surface (`sre-agent/`) in azcapman, including corrected subagent YAML schema and an explicit statement of what an SRE Agent plugin can and cannot deliver.

## Why
All prior plugin surfaces were deleted in commit 449cf07. Prior research found the shipped subagent YAML schema was entirely wrong and that SRE Agent plugins can only contribute Skills and MCP servers (no agents/subagents row) per https://learn.microsoft.com/en-us/azure/sre-agent/plugin-marketplace — meaning `sre-agent/subagent/*.yaml` can never ship via plugin install regardless of schema correctness.

## Known prior findings to verify (not re-derive from zero)
- Corrected subagent schema: `api_version: azuresre.ai/v2` (not v1); `kind: ExtendedAgent` (not AgentConfiguration); `metadata.name` (not spec.name); `spec.instructions` (not spec.system_prompt); `spec.handoffDescription` (not spec.handoff_description); `ExecutePythonCode` (not execute_python) tool name.
- Validate schema claims against the live `sreagent_workflows_validate`/`sreagent_workflows_generate` tools (azure-sreagent MCP domain), not just the (possibly stale) public docs page.
- Per plugin-marketplace docs, a plugin can only ship Skills + MCP servers — subagent YAML is a portal-applied artifact (Builder > Agent Canvas), never installable via plugin.
- `srectl` is unreleased; Microsoft's own lab guidance says not to build automation against it — do not propose any `srectl init`/`post-provision.sh` hook.
- SRE Agent skills DO support bundled supporting files (`files:` frontmatter per https://learn.microsoft.com/en-us/azure/sre-agent/skills), but no official example plugin uses this; all reference plugins are lone ~4KB SKILL.md files.
- Constraints: max 5 concurrent active skills (oldest auto-unloaded), active skills clear on conversation compaction.
- Symlink handling is UNVERIFIED/HIGH RISK for this harness — zero symlinks found across all 7 reference plugins in github.com/Azure/sre-agent-plugins, docs never mention it.

## Acceptance criteria
1. Re-verify each bullet above; use `sreagent_workflows_validate` live if available to confirm schema correctness rather than trusting docs alone.
2. Clearly state the scope boundary: what CAN ship via SRE Agent plugin (skills, MCP servers) vs what CANNOT (subagents) with citation.
3. Do not propose any srectl-based automation.
4. Flag symlink risk explicitly as unresolved/high-risk rather than asserting safety.
5. Return the requirements as a self-contained markdown document with inline citations.

## Research subagent result (received)
Status: **research phase complete, findings received with a major correction.**

- Plugin scope confirmed: skills + MCP servers only, no subagents — https://learn.microsoft.com/en-us/azure/sre-agent/plugin-marketplace (commit f85079a3, 2026-06-04).
- **CORRECTION to prior memory**: the `api_version: azuresre.ai/v2` / `kind: ExtendedAgent` / `spec.instructions` / `spec.handoffDescription` schema could NOT be confirmed against live docs and is contradicted by them. Current https://learn.microsoft.com/en-us/azure/sre-agent/sub-agents and .../create-subagent (commit 734020337b / b8288e33) show a **flat schema**: `name`, `system_prompt`, `handoff_description` (snake_case), `tools`, `connectors`, `enable_skills`/`allowed_skills` — no API-version envelope at all. Subagent portal surface renamed to "Builder > Subagent builder" (was "Agent Canvas").
- `files:` frontmatter key confirmed real (skills page + create-skill tutorial), but reference plugins (datadog, aws) return 404 on raw SKILL.md fetch, so "no files used in practice" claim is unverified either way. Plugins declare `"skills": ["skills/"]` (subdirectory, not bare root) in plugin.json.
- Max-5-concurrent-skills / clear-on-compaction constraint confirmed verbatim.
- No `azure-sreagent` MCP tool was available to the subagent this run — schema claims rest on docs citations only, not live validation.
- Symlinks: still unverified/high-risk — marketplace repo confirmed 7 plugins (datadog, atlassian-rovo, pager-duty, elasticsearch, dynatrace, aws, azure-managed-grafana) but SKILL.md content itself 404'd, so symlink presence/absence inside skill dirs could not be directly re-checked this pass.
- `srectl` release status not re-fetched this pass; no Learn page found (consistent with "unreleased" but not independently re-verified).

**Action needed before documenting this harness for real**: do NOT reuse the api_version/kind/ExtendedAgent schema in any rebuilt `sre-agent/subagent/*.yaml` — use the flat schema instead, and note it's portal-only / non-plugin-installable regardless.

## RESOLVED via GitHub Git Trees API (follow-up pass)
Status: **DEFINITIVE for the reference ecosystem — zero symlinks found. Installer-mechanism behavior for a hypothetical azcapman symlink still not code-tested (no reference plugin exercises the path), but the strong, verified convention is: don't use symlinks at all.**

Source: `https://api.github.com/repos/Azure/sre-agent-plugins/git/trees/main?recursive=true`, tree SHA `484e5ca1108d52bbc09fbf90e0f07681a302608a`, `"truncated": false` (i.e., complete tree, nothing omitted).

- Every entry is mode `040000`/type `tree` (directory) or mode `100644`/type `blob` (regular file). **No entry has mode `120000`** (git's symlink mode) anywhere in the repo.
- Corrected file layout: each plugin's skill file lives one level deeper than previously assumed — `plugins/<name>/skills/<skill_name>/SKILL.md` (e.g. `plugins/datadog/skills/datadog_observability/SKILL.md`), not `plugins/<name>/skills/SKILL.md`. This is why earlier raw-fetch attempts 404'd.
- Every plugin directory contains exactly 4 files: `.mcp.json`, `README.md`, `plugin.json`, and the one nested `SKILL.md` — no supporting reference files, no `files:` frontmatter usage in practice, confirmed across all 7 plugins (atlassian-rovo, aws, azure-managed-grafana, datadog, dynatrace, elasticsearch, pager-duty).

**Conclusion: the official SRE Agent plugin ecosystem uses zero symlinks by convention.** This doesn't prove the installer would break on one (no reference case tests it), but it removes any assumption of safety — the safest and only precedent-backed path for azcapman is to avoid symlinks in the SRE Agent plugin skill directory entirely, same as Codex.
